# Как внести изменение

## Задача и ветка

Выбери открытую [Issue](https://github.com/Dtsyp/FTTC-PROF-DEV-HUB/issues) или заведи её через подходящую [форму](.github/ISSUE_TEMPLATE). Опиши, для кого что должно измениться, как это увидеть и какие проверки нужны. В баге добавь шаги воспроизведения. Для технической задачи укажи затронутую область. Существенные уточнения сохраняй в Issue, чтобы их видел следующий участник.

Прямой push в `main` запрещён. Каждую задачу ведём в рабочей ветке от актуальной `main`. Имя ветки — `тип/номер-краткое-описание`. Допустимые типы: `feature`, `fix`, `chore`, `refactor`, `docs`, `test`, `ci`. Номер берётся из Issue, без `#` и ведущих нулей. В описании используй строчные латинские буквы и цифры, разделяй слова одиночными дефисами.

## От Issue до PR на одном примере

Допустим, Issue **#42** называется `feat: показать преподавателю черновик ИПР`. У преподавателя есть сохранённый черновик. Приёмка требует, чтобы владелец видел его цели, а другой преподаватель даже по прямой ссылке не мог прочитать содержимое.

1. **Проверь рабочую копию.** Посмотри `git status -sb`. Если есть чужие или незаконченные изменения, сохрани их в исходной рабочей копии. Для новой задачи в чистой копии:

   ```shell
   git fetch origin
   git switch -c feature/42-view-plan-draft origin/main
   ```

   Если ветка задачи уже есть локально, перейди в неё через `git switch feature/42-view-plan-draft`. Если она есть только на сервере, после `git fetch origin` используй `git switch --track origin/feature/42-view-plan-draft`.

2. **Реализуй и проверь.** В примере нужны два синтетических пользователя и черновик одного из них. Открой черновик владельцем, затем запроси тот же объект вторым пользователем. Зафиксируй результат интерфейса и серверного запроса. Общие [правила проверки изменений](AGENTS.md) применяются и при работе с AI.
3. **Подготовь коммит.** Проверь список файлов и diff, в том числе то, что попадёт в коммит (`git diff --cached`). Один коммит — одно связное изменение. Формат сообщения — `тип: что изменилось`. Для новой функции используй `feat`, для остальных изменений подходят `fix`, `docs`, `test`, `refactor`, `ci`, `chore`. Пример сообщения — `feat: показать преподавателю черновик ИПР`. У функции префикс ветки — `feature/`, а тип коммита — `feat`.
4. **Открой PR в `main`.** Заполни [шаблон PR](.github/pull_request_template.md). Для примера выше в **теле PR** нужна отдельная строка `Closes #42`. Допустимы также `Fixes #42` и `Resolves #42`. Подставляй реальный номер из ветки. Используй закрывающую ссылку, когда изменение выполняет согласованный объём Issue. Если задача изменилась, сверь критерии с автором до слияния.
5. **Передай на ревью.** В PR приложи команды или ручные шаги и их фактические результаты по критериям. Для примера нужны результаты обеих попыток доступа. Для UI добавь скриншот на тестовых данных. Если обязательная проверка заблокирована, оставь PR в Draft и укажи, что нужно для проверки.

Агент может подготовить изменения и текст PR. Commit, push, публикация PR, merge и production deploy требуют поручения разработчика на соответствующее действие.

## Что останавливает слияние

| Кто проверяет | Что именно |
| --- | --- |
| GitHub Actions | Для PR в `main` проверка `PR conventions` сопоставляет имя ветки и номер в закрывающей ссылке в теле PR. Исходный код проверки — [pr-conventions.yml](.github/workflows/pr-conventions.yml). |
| GitHub Rulesets | Для обычного слияния в `main` требуются успешный `PR conventions`, одобрение владельца кода и разрешение обсуждений ревью. После новых изменений кода прежнее одобрение сбрасывается. Допустимый способ слияния — squash. [Действующие правила main](https://api.github.com/repos/Dtsyp/FTTC-PROF-DEV-HUB/rules/branches/main) · [Владельцы кода](.github/CODEOWNERS). |
| Автор и ревьюер | Сверяют diff с Issue, оценивают достаточность проверок и разбирают последствия замечаний. Отложи слияние при проваленном критерии, серьёзном дефекте или недостающей обязательной проверке. После исправления повтори затронутые проверки и запроси повторное ревью. |

Зелёный `PR conventions` подтверждает оформление PR. Сейчас в репозитории нет сборки приложения и набора прикладных тестов в CI. Когда появится первый исполняемый компонент, добавь в том же PR тест основного сценария и запуск в CI. Укажи команду для локального воспроизведения. Чтобы падение этой проверки блокировало слияние средствами GitHub, владелец репозитория должен включить её в обязательные проверки `main`.
