# ADR-0001. Идентичность факта, версия и передача между модулями

**Предложен 19 ноября 2026.** Технический выбор принимает команда в архитектурном PR. Единицу зачёта, владельцев спорных маршрутов PDF и границы учебных периодов утверждают владелец продукта и методист. До этого можно принять синтетические проверки. Продвижение зависимых задач описано в [плане поставки](../architecture/delivery.md).

## Проблема

У одного выпуска конференции могут быть два URL, письмо и ручная запись преподавателя. Если ключ достижения включает способ импорта, каждое свидетельство способно дать отдельный вклад. Повтор одного сообщения, два независимых подтверждения и два ежегодных выпуска требуют разных решений. Аналогично, два набора рекомендаций могут прийти из разных встреч в один уже отредактированный ИПР. [Сверка с PDF](../architecture/requirements-trace.md), B1-03, B2-02/12/13, X02/03/06/07.

## Владение и идентичность

| Объект | Владелец и идентичность | Инвариант и результат |
|---|---|---|
| Наблюдение / выпуск / карточка | Ingestion хранит источник, устойчивый ключ записи в источнике, версию наблюдения и выпуск. Internal или External Catalog публикует версию карточки и связывает подтверждённые наблюдения с каноническим выпуском | Повтор получения сохраняет выпуск. Ежегодные выпуски с одним URL различаются. Предлагаемое межкаталожное совпадение подтверждает модератор; до решения автоматического объединения нет. У каждого участия один владелец. Алиасы сохраняют происхождение |
| Участие и основания | Каталог-владелец хранит устойчивый participation ID, сотрудника, выпуск, намерение, заявление, решение с версией, автора/основание/время. Действующие свидетельства отдельны от URL, адаптера, версии сообщения | Различаются «интересно», план, отмена плана и заявление участника. У решения есть ожидание, подтверждение, отказ и отзыв; новое подтверждение после отзыва требует новой разрешённой команды и версии. Истёкший дедлайн сам по себе не устанавливает явку |
| Достижение и вклад | Portfolio связывает канонический факт и утверждённый вид зачёта с одним результатом. Ограничение уникальности и проверка версии действуют в БД. Ключ доставки отдельно от ключа бизнес-эффекта | Модератор явно устанавливает связь с ручной записью, сохраняя ручные поля. После отзыва одного основания пересчитываются оставшиеся независимо допустимые основания; снимается только необоснованный вклад. Спор нескольких ролей или пересекающихся каталогов ждёт решения, учёт до разрешения не удваивается |
| Отчётный и целевой периоды | Taxonomy & Periods определяет ID и границы, Portfolio владеет ИПР. Дата мероприятия, решения и включения в отчёт различаются. Meetings хранит ID отчётного и целевого периода | Для границы семестра, многодневного события и позднего факта нужны примеры методиста. «Следующий год» не выводится арифметически из отчётного семестра. Неоднозначная цель блокирует запись |
| Сводка и утверждение | Meetings фиксирует согласованный срез из одной согласованной версии данных: сотрудник, область, период, момент среза, версии источников/правил/шаблона и разрешённые значения, достаточные для воспроизведения | В монолите допускается чтение владельцев в одном согласованном снимке PostgreSQL. При запаздывании проекции сверить версии у владельцев или отложить финализацию; показать дату актуальности. Коррекция даёт новую версию с причиной. Исторический экземпляр подчинён текущей видимости и сроку хранения |
| Перенос рекомендаций | Meetings владеет версией утверждённого набора. Portfolio принимает **набор, версия, сотрудник, целевой период**, ожидаемую версию плана и разрешённые поля; сохраняет связь принятого предложения с черновиком | В одной транзакции выбирается/создаётся допустимый черновик с защитой от параллельного создания и фиксируется применение набора. Для двух встреч, отсутствующего периода, активного плана, ручной правки либо отзыва/замены набора после применения — явный конфликт или предложение с проверкой версии. До согласования допустимого числа черновиков автоматическое создание в неоднозначном случае запрещено. Действующий ИПР не перезаписывается |

Подтверждённое участие с недостающей ролью получает результат **«ожидаются реквизиты»**. Преподаватель или уполномоченный сотрудник видит поле и причину. При дополнении проверяются текущая версия и действующие основания; отзыв закрывает ожидание. До завершения запись не даёт подтверждённого вклада. Пользователю доступны результат команды и отдельный результат применения в портфолио. Ошибки разрешения видны в очереди оператора.

## Контракт обработки

- Простые чтения и действия внутри владельца выполняются синхронно. На границах, требующих повтора, в одной транзакции фиксируются изменение и запись outbox. Конверт содержит ID события, тип и версию схемы, ID и версию агрегата, ID корреляции, время. Приватный текст в универсальный конверт не включается.
- Потребитель атомарно фиксирует обработанную версию/ключ эффекта и доменное изменение. При конкурентной записи обновляет по ожидаемой версии. При повторе отвечает тем же результатом. Старую версию игнорирует после уже применённой новой. При пропуске последовательности запрашивает актуальное состояние у владельца либо ждёт пропущенную версию. Порядок часов на разных процессах не устанавливает причинность.
- Обработчик резервирует задание на ограниченное время. Есть ограниченные повторы, отложенный разбор ошибки и ручной повтор тем же ключом. Падение после фиксации результата и до подтверждения задания не дублирует эффект. Встроенное уведомление имеет собственный ключ адресата, типа, предметного события и версии. Смена срока или отмена инвалидирует предыдущее ожидающее напоминание; непосредственно перед публикацией проверяются срок, версия, получатель и текущая видимость.
- Изменения формы события расширяются совместимыми необязательными полями. При несовместимости сначала разворачиваются читатели обеих версий, затем писатель, после обработки очереди и проверки восстановления выводится старая версия. Неизвестная обязательная версия изолируется с диагностикой без потери записи. Миграция существующих данных идёт через сопоставление оснований, отчёт спорных совпадений, сверку вкладов и ограничение уникальности после разбора. На дату предложения прикладной схемы в main нет.
- Отказ источника, частичный, пустой или устаревший ответ оставляет последнюю подтверждённую публикацию и создаёт проверку актуальности. Разбор выпуска, текущей версии, ручного поля и совпадений выполняется до публикации. Два параллельных обхода и поздний ответ старой версии не заменяют новый дедлайн. Для источника без надёжного порядка наблюдений из конкурирующих конфликтных результатов выбирает модератор. При разъединении ошибочно слитых выпусков переоцениваются связанные основания, планы и ожидающие напоминания с историей.
- Контракт разбора неприменим как разрешение получать любой адрес из карточки. Оператор утверждает канал, ограничения назначений и перенаправлений, расходы и объём данных; каждый запрос, повтор и вложение остаются в разрешённых границах. Изменение схемы или прекращение допуска останавливает соответствующий обход; дальнейшая выдача накопленных контактов зависит от решения владельца данных.

## Варианты и последствия

| Вариант | Корректность, труд и риск | Обратимость и критерий |
|---|---|---|
| Внутренние вызовы и PostgreSQL с outbox только для нуждающихся в повторе эффектов | Один источник правды и короткий путь чтения. Понадобятся ограничения БД, версии, сверка и интерфейс разбора. Реализуемо итерациями тремя разработчиками | Клиентские контракты сохраняют форму при смене очереди. Проверить падение между фиксацией факта и применением, две доставки, отзыв и устаревшую версию |
| Единая синхронная транзакция для всех модулей | Подходит для локального чтения/изменения. Долгий импорт, внешний запрос и отправка в транзакции держат соединения и не убирают неопределённость удалённой операции | Локальные вызовы можно оставить. Для внешнего или отложенного эффекта нужен самостоятельный договор повтора |
| Отдельный брокер и сервис для каждого блока | Изоляция масштабирования требует развёртывания, наблюдения и восстановления дополнительных компонентов; проблему двух оснований и версий брокер не решает | Возвращаться при измеренной задержке очередей или независимом масштабировании. Миграция возможна за существующей границей обработки |
| Уникальность по URL или ключу доставки | Дешевле в первом PR, но смешивает выпуск и доказательство. Ошибка видна после повторного начисления прогресса и включения в сводку | Поздняя миграция требует ручного сопоставления. Приёмочные случаи содержат два источника, два выпуска, ручное основание и отзыв одного |

Критерии будущей реализации включают параллельное подтверждение, повтор после аварии, пропуск версии, восстановление и расхождение двух встреч. Сравнить историю, видимый прогресс, число документов, сохранность ручных полей и значения в проекциях. Эти испытания входят в задачи разработки.

Для исторической сводки несколько запросов с обычным Read Committed могут видеть разные состояния. Использовать одну согласованную транзакционную выборку либо Repeatable Read с зафиксированным набором входов. Разрешение на последующую выдачу всегда проверяется по текущему состоянию. [PostgreSQL, Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html).

При доставке даже первой для Portfolio версии проверяется текущая публикация Meetings и её разрешённая аудитория. Для уже перенесённых полей, предложений конфликтов и печати сохраняется проверяемая связь с источником разрешения. Отзыв видимости поля действует по ADR-0002 независимо от согласования нового содержания ИПР. При недоступном основании поле закрыто.
