# Проверки для ADR-0003

## Локальный запуск FastAPI и PostgreSQL

В Linux или WSL запустите команду из корня репозитория под обычной учётной записью.

```bash
bash docs/adr/checks/0003-fastapi-smoke.sh
```

Нужны Bash, Python 3.13 с `venv` и `pip`, доступ к PyPI, серверные и клиентские утилиты PostgreSQL 17 и свободный локальный порт `55423`. Для другого порта задайте `FTTC23_PORT`. Для другого интерпретатора или каталога утилит задайте `PYTHON` и `PG_BIN` абсолютными путями. По умолчанию скрипт использует `python3.13` и `/usr/lib/postgresql/17/bin`. [Скрипт проверки](0003-fastapi-smoke.sh)

Скрипт создаёт `venv`, пустой кластер и БД `fttc23_test` в закрытом временном каталоге. Uvicorn и PostgreSQL слушают только `127.0.0.1`. Тестовый клиент PostgreSQL использует SCRAM с одноразовым паролем и локально отключённым TLS. При завершении скрипт останавливает сервисы и удаляет каталог. Постоянный каркас и прикладной CI относятся к #26, миграционный путь и разделение ролей — к #27.

### Результаты

Два запуска подряд создали отдельные окружения и кластеры. Во внешнем окружении второго запуска были заданы `PGSSLMODE=require`, другой `PGHOSTADDR` и отсутствующий `PGSERVICE`. В обоих случаях `GET /openapi.json` вернул 200 и описал успешный ответ `GET /probe` как `ProbeResult` с обязательным полем `status`. Затем обработчик выполнил SQL через `postgresql+psycopg` и вернул JSON по реальному HTTP-соединению. Оба запуска завершились с кодом `0`.

```text
No broken requirements found.
alembic 1.20.1
postgres (PostgreSQL) 17.12 (Debian 17.12-0+deb13u1)
Python 3.13.18, FastAPI 0.165.0, Uvicorn 0.54.0, SQLAlchemy 2.1.9, Psycopg 3.3.9
OpenAPI: GET /probe -> ProbeResult
SQL: fttc23_test | 170012 | 1
GET /probe -> 200 application/json {"status":"ok"}
```

Чтобы воспроизвести отказ, запустите тот же скрипт с `--missing-db`. Он создаёт `fttc23_test`, а обработчик обращается к отсутствующей БД `fttc23_missing`. Схема OpenAPI осталась доступной. Запрос `GET /probe` вернул `503 application/json {"detail":"database unavailable"}`, проверка штатного ответа завершилась с кодом `1`. [ADR-0003](../0003-pilot-environment.md)

## Проверка тестового контура ИТМО

План применяется после предоставления тестового доступа ИТМО.

1. **Для #23.** По разрешённому маршруту открыть тестовый HTTPS-адрес и войти вымышленным пользователем через разрешённый клиент. Повторить после смены тестовой почты. Пара «доверенный провайдер, устойчивый субъект» должна сохраниться. Вместе с владельцем провести отзыв назначения по согласованному каналу, включая ручную операцию с аудитом, если её выберет ИТМО. Записать дату, исполнителя и исходы без токенов и персональных данных.
2. **При интеграции #29 и #31.** Проверить один внутренний профиль при повторном входе. Тестовый руководитель читает разрешённый объект преподавателя. После подтверждённого отзыва тот же запрос из старой сессии получает отказ. После деактивации приложение отказывает в новой сессии.
3. **До реальных данных.** Эксплуатация согласует точку, частоту, окно и цель измерения доступности, затем фиксирует долю успешных проб HTTPS и тестового входа. БД и файлы восстанавливают в изоляции, сверяют удаления и отзывы с независимым актуальным реестром и замеряют RPO/RTO. Назначенный владелец разрешает доступ после сверки. Унаследованные задания отправки остаются в карантине до отдельной проверки актуального дедлайна, версии и факта доставки.
