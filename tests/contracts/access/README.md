# Контракты объектного доступа

[Матрица решений](cases.csv) задаёт ожидаемые результаты для реализации серверной авторизации в [#31](https://github.com/Dtsyp/FTTC-PROF-DEV-HUB/issues/31). Каждая строка называет субъекта, действие, объект, состояние и решение до и после изменения. [Фикстуры](fixtures.json) описывают обе стороны назначения, получателей публикации и маркеры данных. В столбце `sources` указаны [разделы и проверяемые фрагменты архитектуры](sources.csv).

## Как воспроизвести строку

1. Подготовить объекты и состояние `before_state`. Войти под `actor`. Для `read` проверить выборку `collection`, запросить карточку по ID и сохранить прямую ссылку. Для печати сделать новый запрос к серверу. Сверить интерфейс и ответы API с `before_result`.
2. Из другой сессии применить `after_state`. Состояния заданы целиком. Одинаковые состояния обозначают контрольный повтор. В первой сессии обновить список, обратиться по сохранённой ссылке и повторить печать либо изменение. Сравнить со столбцом `after_result` на первом же новом запросе.
3. Маркер объекта имитирует содержимое защищённого поля. Искать его и в отображении, и в сырых данных ответа, включая сниппеты, скрытые поля страницы и печатный документ. Для одного поля достаточно тестовой строки из `marker`. У уже открытой вкладки проверяется следующая выдача с сервера. Ранее полученная страница или сохранённый файл могут остаться у пользователя.

### Как читать результаты

| Выборка `collection` | Что проверять в списке |
|---|---|
| `personal-profile` | Собственный профиль в личном кабинете. Если кабинет запрашивает коллекцию, она включает только свой профиль. Если сразу открывается карточка, проверяется её запрос, отдельный список не требуется |
| `supervised-employees` | Только назначенные сотрудники. Когда назначений нет, активный руководитель получает доступный пустой список. Его собственный профиль в эту выборку не попадает |
| `peer-feed` | Лента достижений коллег по заданному треку. И до, и после снятия публикации лента доступна. После снятия в этой выборке ноль карточек |
| `meeting-briefs`, `private-notes`, `published-results` | Список доступных материалов соответствующего класса. Для администратора вкладка настроек шаблонов и служебные метаданные находятся за пределами этой выборки |
| `none` | Строка проверяет запись. Сохранённое значение сверяется отдельным контрольным чтением |

| Решение при `read` | Список в UI и API | Прямая ссылка в UI и API | Новая печать |
|---|---|---|---|
| `visible` | Карточка есть в разрешённом списке. API возвращает её ID с разрешёнными полями списка | Карточка открывается, в разрешённом поле ответа и на экране есть маркер | При повторной загрузке той же карточки действуют её права чтения. Отдельного разрешения сформировать документ в этой строке нет |
| `printable` | У ведущего есть сводка назначенной встречи | Ведущий видит маркер сводки | UI получает печатную версию. API выдаёт разрешённые факты той же сводки с её маркером |
| `read-only` | Сводка по-прежнему в списке | Тот же текст сводки по-прежнему доступен | Действие печати недоступно или завершается отказом. По старой ссылке печати сервер не выдаёт документ и маркер |
| `hidden` | В разрешённом списке отсутствуют объект, его сниппет и вклад в количество или пагинацию. Для закрытого целиком класса материалов встречи допустим отказ в доступе к коллекции | Содержимое недоступно. Сервер отказывает в выдаче объекта, ответ и экран не содержат маркера | Печатная подборка исключает объект. Запрос отдельного документа по его ID не выдаёт защищённых полей или байтов |
| `blocked` | Старая сессия теряет доступ ко всему защищённому списку, включая свои объекты | Сервер отклоняет новый защищённый запрос, UI не показывает вновь выданных данных | Закрыта вся новая защищённая выдача, в том числе старый адрес печати |
| `pending` | **Ожидает решения ИТМО**. До решения действуют проверки `hidden` | Без согласованного основания текст закрыт, включая сохранённый адрес | До решения документ и защищённые поля не выдаются |

Отдельная печатная форма профиля или достижения не требуется для пилота. Если она появится как отдельная операция, адаптер проверяет её собственное разрешение. В данных явное разрешение `print-brief` есть у ведущего для конкретной сводки. Для профиля и достижения в строках `hidden` обязательна проверка отсутствия содержимого и в доступных печатных подборках. HTTP-коды, адреса маршрутов и формат документа выбирает реализация.

Для `edit-goal` изменить одну цель ИПР. Для `edit-recommendation` изменить текст черновой рекомендации назначенной встречи. В каждой фазе отправлять новое значение, например `SYN-<case-id>-before` и `SYN-<case-id>-after`.

| Решение при изменении | Что проверить |
|---|---|
| `written` | UI подтверждает сохранение. Штатный запрос принят. Контрольное чтение показывает отправленное значение |
| `refused` | UI скрывает изменение или сообщает об отказе. Прямой запрос отклонён. Последнее сохранённое значение осталось прежним |
| `blocked` | Следующее сохранение из открытой формы отклонено из-за деактивации. В хранилище сохранилось последнее принятое значение |

Для отказа состояние записи сверяет тестовая оснастка либо независимо уполномоченный читатель. Список и печать относятся к строкам чтения. Изменяющий запрос сам по себе не создаёт эти представления.

## Контрольные переходы для #31

| Сценарий | Какие результаты сравнить |
|---|---|
| Свой и чужой объект | В одной сессии `teacher-a` читает `profile-a`, а замена ID на `profile-b` закрывает выдачу. Тот же `profile-a` закрыт для `teacher-b`. В паре записей ИПР только владелец меняет цель |
| Смена и отзыв курирования | В списке курируемых у `supervisor-a` до перевода есть только `teacher-a`, у `supervisor-b` только `teacher-b`. После перевода первый список пуст, второй содержит обоих. При отдельном отзыве без замены второй руководитель сохраняет только B. Роль преподавателя у первого руководителя даёт чтение своего профиля. Чужой профиль B и отозванный A для него закрыты |
| Деактивация | `disabled-teacher` активен в `before-deactivation`. Переход в `base` с тем же ID закрывает чтение собственного профиля и повторное сохранение открытой формы ИПР |
| Снятие публикации | В `old-achievement-link` явно выбранный получатель `peer` открывает `achievement-a` в ленте по `synthetic-track`. В `index-stale` старый кандидат остаётся в индексе, а действующая публикация уже снята. В следующей выдаче ленты исчезают карточка и её вклад в общий результат. В старой ссылке, новом запросе печати и сырых данных отсутствует `SYN-ACHIEVEMENT-A`. Контрольный преподаватель вне аудитории не видел запись и до снятия |
| Содержание встречи | В `admin-brief` и `admin-private-note` ни один ответ с содержанием не выдаёт администратору `SYN-BRIEF-STAFF-ONLY` или `SYN-NOTE-PRIVATE`. Допустимые служебные метаданные и шаблоны проверяются отдельно от текстов. Назначенный ведущий с явным допуском читает и печатает сводку. После отзыва только печати чтение сохраняется. Отзыв персонального допуска закрывает также изменение черновой рекомендации при всё ещё действующем курировании |
| Опубликованная часть | `teacher-a` видит свой `SYN-RESULT-PUBLISHED`. Сводка, текст приватной заметки и черновая рекомендация не попадают в поля результата, сниппеты или печатную подборку сотрудника |

`peer` — преподаватель, которому в этом примере явно адресовано достижение. `admin` не получал персонального допуска к встрече. Для приватной заметки предусмотрен только синтетический отрицательный пример защищённого материала P3. Применение `transferred` меняет только курирование. Материалы уже прошедшей встречи сохраняют исходные идентификаторы. Примеры не задают организационный порядок передачи прав прежнего ведущего.

## Решения ИТМО

| Строка матрицы | Открытое решение |
|---|---|
| `employee-brief` | Правило чтения и печати самой аналитической записки сотрудником **ожидает решения ИТМО**. Свою опубликованную часть итогов он уже может прочитать. [D-MEET #25](https://github.com/Dtsyp/FTTC-PROF-DEV-HUB/issues/25) |
| `prior-meeting` | После назначения `supervisor-b` читает текущий профиль A. Передача ему истории предыдущих встреч **ожидает решения ИТМО**. В фикстуре он не получал персонального допуска к прежней сводке. ## Проверка набора

Из корня репозитория запустить валидатор на Python 3.9+.

```sh
python3 tests/contracts/access/validate.py
```

Валидатор проверяет уникальность ID и маркеров, типы ссылок в фикстурах и таблице, сочетания операций с результатами, ссылки на решения и наличие каждого фрагмента в указанном разделе документа. Смысл ожиданий сверяется при ревью по [архитектуре](../../../docs/FTTC_PROF_DEV_HUB_Architecture_and_Roadmap.md), [матрице требований](../../../docs/architecture/requirements-trace.md) и [ADR-0002](../../../docs/adr/0002-authorization-and-recovery.md).

В Bash битую ссылку можно воспроизвести на временной копии.

```bash
contract=tests/contracts/access
tmp_dir=$(mktemp -d)
cp "$contract"/{fixtures.json,cases.csv,sources.csv} "$tmp_dir/"
sed -i '/^old-achievement-link,/s/,achievement-a,/,missing-achievement,/' "$tmp_dir/cases.csv"
python3 "$contract/validate.py" "$tmp_dir"
```

Ожидается код 1 и сообщение `old-achievement-link.object: unknown reference 'missing-achievement'`. Исходный набор должен по-прежнему проходить проверку.

Для приёмки работающего приложения разработчик #31 сопоставит ID с тестовыми записями и повторит запросы в той же сессии через реальные UI и API. Отдельные интеграционные проверки #31 охватывают срок назначения, аудит, одновременные изменения, сбои до и после записи во внешний реестр и повтор команды с тем же ID. Проверки выдачи достижений, записок и печати выполняются по мере появления соответствующих модулей.
