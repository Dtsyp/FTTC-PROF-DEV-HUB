# Эталоны карточек каталогов

[internal.json](internal.json) содержит внутренние возможности ИТМО, [external.json](external.json) — внешние мероприятия. Каждый файл можно загрузить отдельно. Все организации, контакты, объявления и ключи вымышлены. Адреса в зоне `.invalid` служат идентификаторами примеров. Проверка работает без сети и backend.

## Состав полей

В `required_fields` ключи предназначены для кода, а подписи дословно соответствуют таблицам PDF. Эти ключи задают состав `cards.<сценарий>.fields`. Все поля присутствуют даже в неполном примере, чтобы потребитель мог показать причину пропуска.

| Набор | Таблица исходного PDF ИТМО | Строка матрицы | Обязательных полей |
| --- | --- | --- | ---: |
| Внутренний | §4.3, п. 3, с. 8–9 | B3-02 | 13, включая `opportunity_type` |
| Внешний | §5.3, п. 3, с. 10–11 | B4-02 | 16. Классификатор `event_type` расположен рядом с `fields` |

SHA-256 сверенного PDF — `57c939a51762dc0f85023fd232c030015826300b40bb42303411caf8213653bf`. Состав и назначение полей также сверены с §4.2 [архитектуры](../../../docs/FTTC_PROF_DEV_HUB_Architecture_and_Roadmap.md) и [матрицей требований](../../../docs/architecture/requirements-trace.md).

## Как читать одну карточку

`source` указывает на версионированный снимок в `sources`. От него происходят значения полей и внешний классификатор. В снимке есть поставщик, идентификатор записи, обозначение выпуска организатором, версия, URL и короткая выдержка. У конфликтующих вариантов свой `source`. В примере семинара на одной странице обнаружены две недатированные редакции. Обе относятся к одному выпуску и дают разные сроки регистрации.

| Данные поля | Что проверяет модератор | Ожидаемая причина в `blockers` |
| --- | --- | --- |
| Обычное значение | Значение подтверждено основным снимком. Для цены и числа участников допустим подтверждённый ноль. | Поле отсутствует в списке причин |
| `state: unknown` | В `note` указано, каких сведений не хватает. Если часть срока известна, `raw` сохраняет исходный текст. | `unknown` |
| `state: conflict` | У каждого варианта в `candidates` есть значение и основание. Требуется выбрать достоверный вариант. | `conflict` |
| `state: not_applicable` | Источник считает поле неприменимым. Допустимость исключения для этого типа ещё должен подтвердить владелец требований. | `pending_24` |

Передайте каталогу или экрану модерации `fields` карточки, ссылку `source`, таблицу снимков `sources` и контрольное время `as_of`. Для внешнего события передайте также `event_type`. Сравните результат с `expected`. В `known_fields` посчитаны только подтверждённые обязательные поля. Если `blockers` пуст, `pass_completeness` разрешает следующий этап проверки карточки. Решение о публикации принимается отдельно. При `moderation` версия остаётся у модератора с причинами по каждому полю. Внутреннее поле `status` описывает состояние набора у организатора.

Для дедлайнов контрольное время `as_of` зафиксировано в самом наборе. В полном внешнем примере у обоих сроков местное время 12:00. В 10:00 UTC приём тезисов уже закончился в 09:00 UTC, а регистрация ещё открыта до 11:00 UTC. Оба срока засчитываются в полноту. У следующего выпуска указан только срок регистрации. У неполной внутренней карточки есть местное время без пояса. В обоих случаях для неустановленного срока ожидается `utc: null`.

В полном внешнем примере организатор прямо указал бесплатное участие, ноль зарегистрированных на момент объявления и отсутствие индексации. Число участников относится к сведениям организатора о конкретном выпуске. В следующем году у цены и числа участников состояние `unknown`. У отдельного вебинара спорная применимость индексации — единственная причина модерации. Во внутреннем наборе так же проверяется непрерывный приём заявок на стажировку. Исключения по типам ожидают [решения #24](https://github.com/Dtsyp/FTTC-PROF-DEV-HUB/issues/24).

## Как воспроизвести импорт

Начните с пустого каталога и по порядку передавайте карточки из `imports`. После каждой доставки сравнивайте ключ выпуска с `expected_key`, а число учтённых выпусков, включая ожидающие модерации, — с `expected_count`. При собственных непрозрачных ID адаптер теста может сопоставить первый полученный ID с эталонной меткой, а затем проверять равенство и различие ID.

Первые два шага повторяют один снимок. На третьем шаге тот же поставщик на той же странице обновил запись для следующего года. `record_id` сохраняется, а `edition_ref` меняется. Ожидаемое число выпусков после этих шагов — 1, 1, 2. У внешней серии `first_held_year` остаётся 2022 в обоих годах. В этих примерах идентичность задают `provider`, `record_id` и `edition_ref`. Правила для реальных источников согласуются в #24. Основания для проверки повторов и годовых выпусков приведены в [ADR-0001](../../../docs/adr/0001-domain-events-and-periods.md).

Из корня репозитория запустите проверку на стандартной библиотеке Python 3.

```sh
python3 -B tests/contracts/catalog/test_catalog.py -v
```
